# Design

> Historical design discussion from 26 September 2026. The active design is
> [`docs/design.md`](../design.md); this file includes proposals that were not
> implemented, including the earlier 1° Open-Meteo grid.

Phase 1 is documents only. No daemon is in this tree. The shape below is what v0 should implement, and it is sized from `sources.md` and `budget.md`.

## Language

Python 3, dependencies pinned with [uv](https://docs.astral.sh/uv/) (`pyproject.toml` plus `uv.lock`). This Mac has Python 3.14.7 and `uv` on `PATH`. Target **3.12 or newer** so later eccodes wheels still install. v0’s runtime dependencies should stay small: an HTTP client that stores response headers (`httpx` is the intended one) and the standard library. GRIB decoding is not a v0 dependency.

The process is a short-lived job, not a resident server. It acquires a file lock, pulls what is due, writes files, and exits.

## What Isobar reads

Isobar stays a menu-bar app. It does not grow a network client for model grids. The contract is a directory on disk.

```text
~/Data/isobar/
  status.json          # one screen of health
  manifest.json        # what is safe to read
  attribution.json     # licence ledger
  raw/                 # immutable bytes as fetched
  products/            # normalised, replaceable
```

No HTTP server. A reader that sees a missing manifest entry skips that layer. Writes are temp-file plus rename, so a crash never leaves a half JSON that looks current.

`manifest.json` carries `"notice": "Situational awareness only — not a flight briefing"`. Isobar shows that line. It is situational awareness for a pilot and a kiteboarder, not a briefing. The daemon does not fetch NOTAM or NAIPS, does not choose a runway, and does not keep the US `fltCat` field aviationweather attaches to a METAR.

### `status.json`

One object Isobar can render as “ECMWF 18Z · 6 h ago”. Times are UTC.

```json
{
  "updated": "2026-09-26T04:40:00Z",
  "sources": [
    {
      "id": "open-meteo-ecmwf-ifs025",
      "ok": true,
      "run": "2026-09-25T18:00:00Z",
      "available": "2026-09-26T01:13:00Z",
      "label": "ECMWF 18Z · 6 h ago",
      "detail": ""
    }
  ]
}
```

`label` is preformatted so the app does not reimplement age. `ok: false` keeps the last good `run` and puts the error in `detail`. Stale is not the same as failed: a source inside its normal delay (IFS 0.25° was 7.2 h after 18Z on the day this was checked) is `ok`.

### `manifest.json`

Each product: `id`, `path` relative to `~/Data/isobar`, `valid_time`, `run`, `units`, `grid` or `stations`, `sha256`, `licence_id` and `licence_ids` pointing into the ledger. A mixed file, such as an aerodrome or kite product that embeds Open-Meteo fields, lists every licence that has to travel with it. Isobar draws only paths listed here. A run is listed only after its required artifacts are in place and `current.json` names that run.

### `attribution.json`

Append-only ledger, one row per source id:

| Field | Example |
| --- | --- |
| `licence_id` | `open-meteo-cc-by-4.0` |
| `policy_url` | the URL quoted in `sources.md` |
| `attribution` | “Weather data by Open-Meteo.com” with `https://open-meteo.com/` |
| `redistribute` | `false` for Bureau anonymous-FTP products |

Bureau FTP material is personal use and must not be supplied to anyone else (`sources.md`). The ledger flag is what a later export command checks. Open-Meteo and ECMWF Open Data are CC BY 4.0 and may be shared if the attribution travels with them. NOAA GFS on the NWS disclaimer is public domain with the three limits quoted in `sources.md`. RainViewer needs the RainViewer credit and is personal or educational only. OurAirports runway rows are public domain; credit is optional. Shore bearings cite OpenStreetMap under ODbL. The marine product also stores the Open-Meteo sentence that the tide series is not for coastal navigation.

## Scheduler

One loop, driven by a table in code, not by a cron expression per file.

For each source: `not_before` (earliest poll), token bucket, watermark of the last stored run or `Last-Modified`.

**When to poll.** Open-Meteo forecast bodies do not support conditional GET. Poll `meta.json`, which returned 304 with `If-None-Match`. A new `last_run_initialisation_time` is a new run. The Open-Meteo model-updates page says to wait 10 minutes after `last_run_availability_time` before trusting every server. Bureau FTP and aviationweather use `Last-Modified` or `ETag` and skip the body on 304 or an unchanged size and time.

**Token buckets.** Capacity and refill come from the published limit, slightly under it.

| Source | Bucket |
| --- | --- |
| Open-Meteo, all hosts together | 600 calls/min, 5,000/hour, 10,000/day, 300,000/month |
| aviationweather.gov | 100 requests/min, and in practice a few an hour |
| RainViewer | no numeric cap was published; cache the maps JSON and do not walk the tile pyramid |
| ECMWF Open Data portal | 500 concurrent connections; v0 does not use it |
| Bureau anonymous FTP | no numeric cap in the Feb 2026 guide; one connection, products only as often as they update |

Open-Meteo **calls are not HTTP requests**. The pricing-page formula in `sources.md` multiplies by location count. A national grid is thousands of calls even when it is one URL. The minute bucket has to count weighted calls. A 1° Australian grid is about 1,800 calls, so it cannot go out as a single burst against a 600/minute cap. Chunk at 250 locations. A minute that also sends the point bundle (about 35 weighted calls) then stays under half of 600. Sixteen locations in one URL is the largest mix that was actually requested; 250 is a budget choice, not a load test. Space the chunks by at least a minute.

**Backoff.** On 429 or 5xx, and on a transport error after the request was sent, count the attempt against the token bucket. Do not give the tokens back: the provider already saw the request. Honour `Retry-After` when it is present. Otherwise use exponential delay with full jitter, cap 30 minutes. Persist that deadline and a per-source circuit breaker in `state.json` so a restart or a wake does not immediately retry. On 304, write nothing. A Bureau IP block is a stop, not a retry storm: surface it in `status.json` and do not rotate user agents to get around it.

**Idempotent writes.** Object key is `source + run init + valid time + variable`, or `source + Last-Modified + content hash` for files that are not model runs. If the hash matches what is stored, do not rewrite the product. Raw bytes are stored once under that key.

**User-Agent.** `isobar-data/<version> (personal; Perth)`. aviationweather.gov asks for a custom agent so filters do not treat the client as anonymous noise. Do not send a browser agent to look like a person.

## Storage

### Raw

Immutable. Path includes the key above. Compress JSON and XML with zstd if the body is over about 32 KB. Do not recompress GRIB in v0 because v0 does not store GRIB. Bureau tarballs stay as the `.tgz` the Bureau wrote.

Keep raw long enough to reprocess a bad normaliser, not as the archive. Recommended: **3 days** for Bureau state tarballs (the product itself is a 72-hour snapshot; keeping 14 days of identical overlap is the disk hog in `budget.md`). **14 days** for Open-Meteo JSON and aviation text, which are small.

### Normalised grids

v0 file, one per variable per valid time:

```text
products/grids/ecmwf_ifs025/20260925T18Z/mslp/20260926T06Z.f16
products/grids/ecmwf_ifs025/20260925T18Z/mslp/20260926T06Z.json
```

The `.f16` is little-endian IEEE float16, row-major, north to south, west to east. The sidecar JSON has `lat0`, `lon0`, `dlat`, `dlon`, `ny`, `nx`, `units`, `run`, `valid_time`, `model`, `fill` (NaN bit pattern is not reliable in float16; use a documented sentinel such as −32768 and a `fill` field). Missing Open-Meteo nulls become that sentinel.

This is enough for isobars and an 850 hPa shade. Zarr or NetCDF waits until a GRIB decoder is actually writing chunks. Float16 is the storage type; contouring should promote to float32.

Request Open-Meteo with `cell_selection=nearest` and `elevation=nan` repeated once per coordinate. Otherwise the API downscales toward a land cell and the “grid” is not the model grid. That pair was what returned −32.00, 115.75 for IFS 0.25°.

Domain for v0: 10°S–45°S, 110°E–160°E, **1.0°**. That is 36 × 51 = 1,836 points. Ten variables, which is the top of the weight plateau (`budget.md`): `pressure_msl`, `temperature_850hPa`, `precipitation`, `wind_speed_10m`, `wind_direction_10m`, `wind_gusts_10m`, `cape`, `cloud_cover`, `visibility`, `weather_code`. An eleventh name would multiply every one of the 1,836 calls. Request `wind_speed_unit=kn` and record knots in the sidecar. Horizon: 48 hours. **Two runs a day, 00Z and 12Z**, after `meta.json` says the run is 10 minutes past availability. Four runs would be 7,344 calls before anything else and would leave less than half the daily cap. The 06Z and 18Z cycles stay out until that rule is reopened. IFS 0.25° native step is 3 hours; asking the API for hourly values invents steps. Store every 3rd hour and do not pretend the interpolated hours are model output. The sidecar should say `native_step_hours: 3`.

Ensemble spread is **not** this grid. It is two points: Swanbourne, whose Bureau JSON gave −32.0, 115.8, and Sydney Observatory Hill (WMO 94768). Read that station’s latitude and longitude from `IDN60901.94768.json` or the NSW bundle on the first pull, and cache them. v0 may hardcode the two WMO ids. Members: `ecmwf_ifs025_ensemble`, `pressure_msl` and `temperature_850hPa`, 7 days. Product is mean, min, max, and the 10th–90th percentile, stored as JSON next to the point. Keep the member matrix in raw for 14 days so the percentiles can be recomputed. A 51-member national grid does not fit the free quota.

IFS 9 km (`ecmwf_ifs`) is a point product, not a grid. A national sample of it is the same location-weighted billing as 0.25°. v0 requests it at up to eight coordinates, four runs a day, because a beach wind and a sea breeze are local and the national grid is only on 00Z and 12Z. Defaults, all on distinct cells in the five-point check except YSSY, which was not in that call:

| Id | Request | Role |
| --- | --- | --- |
| `cottesloe` | −31.9953964, 115.7511955 | Beach forecast. Onshore-from 270°. |
| `safety-bay` | −32.3040595, 115.7286309 | Beach forecast. Onshore-from 235°. |
| `rottnest` | −32.0, 115.5 | Offshore end of the sea-breeze pair. |
| `perth-airport` | −31.9403, 115.967003 | Inland end. Also the YPPH surface wind. |
| `garden-island` | −32.2, 115.7 | South coastal cell, distinct from Safety Bay. |
| `yssy` | −33.946, 151.177 | Sydney surface wind. |

Hourly fields, `wind_speed_unit=kn`, horizon 72 hours: `temperature_2m`, `dew_point_2m`, `pressure_msl`, `wind_speed_10m`, `wind_direction_10m`, `wind_gusts_10m`, `precipitation`, `cape`, `visibility`, `cloud_cover`, `cloud_cover_low`, `weather_code`, plus `daily=sunrise,sunset`. That is 14 names, weight 1.4. The 9 km meta step is 1 hour and a 72-hour wind series came back hourly and non-null, so these hours are stored as model hours. Do not add pressure-level names to this request.

Upper air is a second request, `ecmwf_ifs025`, `wind_speed_unit=kn`, up to eight aerodromes, four runs, 72 hours, native step 3 h. Defaults are YPPH and YSSY. Fields are requested at 1000, 925, 850, 700, 600, 500, 400, 300, 250, 200, 150, 100 and 50 hPa: temperature, wind speed, wind direction, geopotential height, relative humidity, cloud cover and vertical velocity. Open-Meteo's `vertical_velocity_*hPa` is geometric vertical velocity in m/s; it is derived from ECMWF omega and temperature, so it is stored as `vertical_velocity_ms`, not as native omega. The request is 91 hourly variable names. Pressure-level cloud cover is an estimate from relative humidity, not a TAF cloud base. Do not request `freezing_level_height` or `cloud_base`.

The ninth aerodrome or the ninth surface point is refused. The cap is what `budget.md` counted.

### Observations

Append-only SQLite, `products/obs/obs.sqlite`, unique on `(wmo, aifstime_utc)`. Columns match the Bureau JSON names the popover uses: temperature, wind direction and speed, gust, MSL pressure, tendency, rain trace, plus `cloud_base_m`, `vis_km`, `wind_spd_kt`, and `gust_kt` when the station sends them. A null cloud base stays null. Source product id on each row (`IDW60910` versus a later capital-city file). WAL mode. The job inserts and ignores conflicts, so a re-fetched tarball is safe.

v0 bundles: `IDW60910.tgz` (verified 2.94 MB at 04:35Z) and `IDN60910.tgz` (NSW and ACT, size not measured). Half-hourly, which is the guide’s “approximately x:05 and x:35”. Skip the download when FTP `Last-Modified` and size match the previous pull.

### Charts and warnings

`products/charts/IDG00073.pdf` and `IDG00074.gif`, plus the previous issue under `previous/`, because Isobar crossfades the last two prognosis issues. Pull from anonymous FTP when `Last-Modified` changes. Do not pull `IDY00050`; it was not on the FTP paths that were tried.

Warnings: FTP XML for the WA and NSW products named in the anonymous product list, into `products/warnings/{id}.xml`. Isobar’s red dot can read those files instead of `api.weather.bom.gov.au`, which the daemon must not call.

### Aviation

`products/aviation/{icao}.json` for each configured aerodrome, default YPPH and YSSY, cap eight. One METAR request and one TAF request cover the whole list. Hourly METAR, TAF on the hour and again if a manual check finds a new `dbPopTime`. Keep the raw text. Parse wind from `wdir` and `wspd` (degrees true, knots). Parse visibility from the raw group, in metres. Ignore JSON `visib` when it is `6+` and the raw text says `9999`. Cloud base is `clouds[].base` in feet. Ceiling is the lowest `BKN` or `OVC`. `SCT` and `FEW` are layers, not a ceiling. `CAVOK` is no ceiling and visibility at or above 10 km. Drop `fltCat`. The file repeats the manifest notice.

The trend is the daemon’s own series, not a second query. Cloud base and visibility for the last 48 hours of stored METARs are the pilot’s trend. Bureau `cloud_base_m` and `vis_km` from the obs table are a second series where the station reports them. Perth Airport 94151 did; the coastal AWS in the phase 1b sample did not. Model `visibility` and `cloud_cover` from the 9 km point sit beside that series and are labelled as model fields. They are not a forecast ceiling.

Crosswind, for every runway end in `products/aviation/runways.json`:

```text
δ = wrap(wind_direction_true − runway_heading_true) to [−180, 180]
crosswind = speed × sin(δ)    # positive from the pilot’s right
headwind  = speed × cos(δ)    # positive is a headwind
```

Speed is the METAR wind, and again the gust when `wgst` is present. The worked hour is YPPH `14013KT` against the OurAirports true headings: runway 21 has a 7.6 kt headwind and a 10.5 kt crosswind from the left; runway 06 has a 2.0 kt headwind and a 12.8 kt crosswind from the right; 03 and 24 are tailwinds. YSSY `03015KT` has a headwind on 07 (10.8 kt head, 10.4 kt cross) and on 34 (11.1 kt head, 10.0 kt cross). The file lists every end. It does not say which runway is in use.

Freezing level, in the same aerodrome file, is the interpolated height in metres from the 0.25° profile. On the checked hour it was 2362 m. If 850 hPa is already below 0 °C, interpolate between 850 and 925, or 925 and 1000. If every stored level is below 0 °C, store null and say the freezing level is below the lowest level. Do not extrapolate.

SIGMET: the worldwide JSON no more than twice an hour, keep features whose `firId` is YMMM or YBBB, into `products/aviation/sigmet.json`. PIREP for YPPH returned 204; call it once an hour anyway and store an empty list. The docs say PIREPs are mostly US and North Atlantic, so emptiness is a normal result, not a failure. AIRMET is not requested.

`products/aviation/runways.json` is the filtered OurAirports rows: ident, both true headings, length, displaced threshold, `closed`. Refresh when the ICAO list changes or a weekly HEAD sees a new `Last-Modified`. The world CSV is about 4.0 MB and need not be kept after the filter.

### Kite spots

`products/kite/{spot}.json` for `cottesloe` and `safety-bay`, and for any added spot under the cap of eight. Each file joins the 9 km hourly series, the marine series, and the derived fields. Marine is its own Open-Meteo request: omit `models`, set `cell_selection=sea`, up to four points, the fourteen fields in `sources.md`, 72 hours, four runs. Store the snapped latitude and longitude. The Safety Bay request snapped offshore of the beach; the file shows that snap so a reader does not treat it as the bay behind the islands.

Shore class, for wind direction θ and the spot’s `onshore_from_deg` (270 at Cottesloe, 235 at Safety Bay):

```text
δ = wrap(θ − onshore_from) to [−180, 180]
|δ| ≤ 45°    onshore
|δ| ≤ 90°    cross-on
|δ| ≤ 135°   cross-off
otherwise    offshore
```

Those cuts are the v0 convention. They are 45° wide, which is coarser than the few degrees in the shoreline measurement. Gust factor is gust divided by sustained speed when speed is at least 1 kt, otherwise null. At 13:00 AWST on 26 Sep the Cottesloe cell was 15.6 kt, gust 21.2, from 119°. δ against 270° is −151°, so the class is offshore, and the gust factor is 1.36. Swanbourne’s 05:00Z observation was 12 kt gusting 22, factor 1.83. The factor is displayed. It is not a default gate.

Daylight is the sunrise and sunset on the 9 km response. The rideable window does not call a second astronomy service.

**Rideable window.** For each of the next 72 hours, an hour qualifies when speed is inside the user band (default 15–30 kt, inclusive), the shore class is not in the excluded set (default: offshore only), and, unless the user turns it off, the hour is between sunrise and sunset. Gust limit is optional and unset. A window is a maximal run of qualifying hours. Empty is a normal result: that Cottesloe hour was inside the speed band and still excluded by direction. The file lists start, end, peak knots, and the classes inside the run.

**Sea breeze.** House defaults, not a Bureau threshold. A page that defined Fremantle Doctor onset speed and direction was not among the pages fetched, so the numbers live in config. A sea-breeze hour at Cottesloe is a 9 km hour whose direction is in 200–250° inclusive and whose speed is at least 5 kt above the Perth Airport 9 km speed. Onset is the first such hour of the local day that follows an hour that was not one. Strength is the coastal speed and gust at onset, and the maximum coastal speed while the condition holds. The label in the file is `sea-breeze`. Through 19:00 AWST on 26 Sep the Cottesloe cell stayed 12–16 kt from 119–145°, which is outside 200–250°, so that afternoon has no onset. Observations can confirm it after the fact: map the 16-point Bureau direction to the centre of its sector (±11.25°) at Swanbourne, Rottnest, and Hillarys, and compare with Perth Airport 94151. That check does not create a second onset time.

**Tide.** `sea_level_height_msl` from the marine request. High and low are the hourly local maxima and minima over the 72 hours, with the Open-Meteo caution stored in the file: not for coastal navigation, not a nautical almanac. Bureau tide pages are not fetched. The rideable window does not require a tide stage unless the user sets one.

Coastal observations named in the spot file, read from the obs table rather than a new download: Rottnest 94602, Swanbourne 94614, Garden Island 95607, Hillarys 95605, Perth 94608, Perth Airport 94151. Ocean Reef has no id in the sources check. Hillarys is the stand-in on the Perth observations page.

### Retention

| Class | Keep |
| --- | --- |
| Raw Open-Meteo, aviation, warning XML, charts | 14 days |
| Raw ECMWF open-data GRIB | 48 hours |
| Partial downloads (`*.partial`) | 1 hour |
| Aviation METAR history | 14 days |
| Raw Bureau tarballs | 3 days |
| Grid float16, all stored lead times | 14 days |
| Grid thinned: MSLP and 850 hPa at the native 3 h step, one file per valid time, latest run only | 1 year |
| Obs SQLite | 1 year, then drop rows |
| Ensemble member matrix (raw) | 14 days |
| Ensemble percentiles at the two points | 1 year |
| Kite and aviation derived JSON, runway filter | 14 days, except the notice and the ledger |
| `attribution.json`, `status.json` | last copy only; ledger rows are not deleted when products expire |

The year-thin grid stays MSLP and 850 hPa, about 21 MB. The other eight grid fields follow the 14-day retention. Ten float16 fields for 14 days of two runs is about 16 MB (`budget.md`). A kite or aviation JSON is kilobytes. ECMWF GRIB is kept for 48 hours, not 14 days. The store stops at 8 GB. A fetch does not start when the volume has under 20 GB free.

## Where it runs

### Now: this Mac, launchd

`scripts/install-launchd.sh` copies the package and a uv virtualenv to `~/Library/Application Support/isobar-data` and writes a LaunchAgent in `~/Library/LaunchAgents`. The plist points at that copy. `StartInterval` is 900 seconds. The script does not load the agent. The job exits in a few seconds when nothing is due. Its log is rotated by the wrapper before each start. Sleep skips intervals. On wake, the next start runs catch-up, still honouring the persisted backoff:

- Open-Meteo: if `meta.json` shows a run newer than the watermark, fetch it. If the previous run is missing and its `meta.json` init is still the one before, fetch that too, so Isobar can crossfade. Do not walk a weekend of runs; Open-Meteo’s useful question on wake is “what is current”.
- Bureau FTP: one pull of each tarball and chart if `Last-Modified` moved. The 72-hour file still contains the observations the Mac slept through.
- Aviation: one METAR/TAF request for the configured list, and SIGMET if it is due.
- Points: one 9 km surface request, one 0.25° upper-air request, and one marine request, if `meta.json` on that host has a new run.

Cost is electricity. Latency to the Bureau from this machine was about 0.1–0.2 s, Open-Meteo about 1.2 s, aviationweather about 0.35 s. The failure mode is a closed laptop during the few hours after a model run, which catch-up covers for “latest”, not for a perfect 6-hourly archive.

Disk is `~/Data/isobar` on the internal drive. v0 is well under 10 GB with the retention above. A GRIB archive is not.

### Later: a small always-on host

Worth it when sleep gaps show up in `status.json` as missed runs the owner cared about, or when v1 starts storing GRIB. A 2 GB machine with 40 GB of disk is enough for v0 and for one ECMWF step at a time. It is not enough to keep every IFS step: an unmeasured extrapolation of the 129 MB step-0 file across an 85-step 00Z run is about 10 GB per run, four runs a day.

A current VPS price was **not** verified. The Hetzner Cloud HTML fetched on 26 Sep 2026 did not include a plan table, and `https://api.hetzner.cloud/v1/pricing` returned 401 without a token. Do not budget a made-up euro figure. The shape is: one shared vCPU, a couple of gigabytes of RAM, tens of gigabytes of disk, a few dollars to a few tens of dollars a month at typical 2026 cloud lists, to be checked on the day it is bought.

The host would pull, write the same directory layout, and sync `products/` plus `status.json` and `manifest.json` to the Mac (rsync over SSH). Raw GRIB can stay on the host. The Mac still sleeps; the files are simply there when it wakes.

### Not the primary: GitHub Actions

From <https://docs.github.com/en/billing/managing-billing-for-github-actions/about-billing-for-github-actions>, fetched 26 Sep 2026:

- “GitHub Actions usage is free for self-hosted runners and for public repositories that use standard GitHub-hosted runners.”
- Private repositories: the plan table lists 2,000 minutes for GitHub Free and 3,000 for GitHub Pro. Past that, Linux 2-core is $0.006 per minute and Linux 1-core is $0.002 per minute on that page.
- Larger runners are billed even on public repositories.

A 15-minute Bureau obs pull does not fit a free private quota (about 2,880 minutes a month if each run lasts a minute). Actions has no durable disk the Mac can treat as `~/Data/isobar`. A public repo must not receive Bureau files: the copyright notice says not to supply that material to any other person. Open-Meteo grids could be published with CC BY attribution, and that is a different product from this personal archive.

Actions is a reasonable later place to rebuild a derived, non-Bureau file on a schedule. It is a bad home for the daemon.

## What v0 deliberately does not do

- No Bureau website crawler, no `api.weather.bom.gov.au`, no Bureau radar, no Bureau satellite JPG, no Bureau tide page, no Bureau AIRMET page, no GPWT page.
- No NAIPS and no NOTAM.
- No GRIB download and no eccodes.
- No ensemble grid, no 0.25° national grid, no ACCESS-G, no 06Z or 18Z national grid.
- No tile pyramid cache beyond the RainViewer frames v1 might add. v0 does not fetch RainViewer yet; the terms are recorded so v1 can.
- No service account, no API key, no paid Open-Meteo plan. The free tier’s ensemble inclusion is why. The Standard plan at €29/month drops ensemble.
